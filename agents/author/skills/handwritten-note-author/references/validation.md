## 1. Transactional append protocol

The append-only guarantee is only worth stating if it is checkable. Nine steps,
all implemented by `scripts/verify_append_only.py`:

1. Resolve and validate the canonical target path (vault-relative, no `..`,
   symlinks resolved, still inside the vault, Markdown extension).
2. Record the original byte size and SHA-256.
3. Prepare the append in a temporary file, never in place.
4. Re-hash the target immediately before writing.
5. Abort if the hash changed — that is concurrent modification, not a conflict
   to merge.
6. Replace atomically (`os.replace` within the same directory), or the safest
   available equivalent.
7. Verify the complete original byte sequence is still an unchanged **prefix**.
8. Verify the agent-block boundaries: exactly one start marker and one end
   marker for the id, start before end.
9. If any invariant fails, report the failure and stop. Never attempt a
   destructive "recovery"; restoring is the user's decision, from version
   control or backup.

```bash
cd "$SKILL/scripts"

# steps 1-2
python3 verify_append_only.py plan --vault "$VAULT" --target "AI/Note.md" --json

# steps 3-9 (markers are generated by the tool, so a block cannot be left open)
python3 verify_append_only.py append --vault "$VAULT" --target "AI/Note.md" \
        --payload /tmp/block-body.md --expect-sha "<sha from plan>" --json

# step 7-8 again, standalone, for the report
python3 verify_append_only.py verify --vault "$VAULT" --target "AI/Note.md" \
        --original-sha "<sha>" --original-size "<bytes>" --block-id "<id>" --json
```

Notes:

- `--payload` receives the **block body only**. Markers are added by the tool; a
  payload containing markers is rejected.
- `--expect-absent` replaces `--expect-sha` when creating a new note.
- `--dry-run` runs every check and writes nothing — use it to rehearse.
- Exit `2` means *blocked* (usage, path security, capability), not *failed*.
  Never re-run with a "cleverer" path after a path-security rejection.

## 2. Revising a runtime block

Permitted only when the user asks, and only for a block whose id was issued in
this run. The invariant is that everything outside the block is byte-identical:

```bash
cp "$VAULT/AI/Note.md" /tmp/before.md      # snapshot first
# ... edit only inside the block ...
python3 verify_append_only.py verify --vault "$VAULT" --target "AI/Note.md" \
        --mode outside-block --block-id "<id>" --original-file /tmp/before.md --json
```

## 3. Capability discovery

Discover; never assume. In particular, do not assume the Obsidian CLI can switch
views, reach developer tools, or capture screenshots — installed versions
differ.

1. Check whether an `obsidian` command exists on `PATH`.
2. If it exists, run its help output and read the **actual** subcommand list.
3. Use only subcommands that appear there.
4. Record which capabilities exist. That record decides the statuses in
   section 4.

MUST NOT install, update, enable, or reconfigure Obsidian, its CLI, plugins,
themes, or dependencies to obtain a missing capability (`AGENTS.md`,
"Ownership, immutability, and authorization"). Ask instead.

## 4. Validation matrix

| Layer | Runs | Tool | Establishes |
| --- | --- | --- | --- |
| Static structural | Always | `scripts/validate_note.py` | Fences, math delimiters, LaTeX structure, agent blocks, embeds, links, path containment, empty assets, SVG validity, placeholders |
| Append integrity | Every write | `scripts/verify_append_only.py` | Prefix preservation, block boundaries, no concurrent modification |
| Transcription fidelity | Always | Human/agent re-reading of the pages against the note | That the note says what the page says |
| Source-level technical audit | Only when requested or clearly in scope | Reasoning, optionally arithmetic recomputation | That a source claim is or is not internally consistent — reported, never applied |
| Obsidian rendering | Only when a real renderer is controllable | Obsidian CLI | That the note renders |
| Mermaid rendering | Only when Obsidian rendering is available | Obsidian CLI | That diagrams draw without errors |
| Excalidraw/SVG rendering | Only when Obsidian rendering is available | Obsidian CLI | That figures appear, unclipped |
| Screenshot visual check | Only when screenshot capture exists | Obsidian CLI + image inspection | Layout, contrast, clipping, scale |

Static checks are heuristic. Passing them proves the note is well formed; it
proves nothing about transcription fidelity, mathematical correctness, or
rendering. Keep those claims separate.

Static run:

```bash
python3 validate_note.py --vault "$VAULT" --target "AI/Note.md" --json
python3 validate_note.py --vault "$VAULT" --target "AI/Note.md" --check embeds svg-validity
python3 validate_note.py --vault "$VAULT" --target "AI/Note.md" --list-blocks
```

Validator regression tests (temporary fixtures only — never point them at a real
vault):

```bash
cd "$SKILL" && python3 -m unittest discover -s scripts/tests -t scripts/tests
```

## 5. Statuses

Every reported item carries exactly one:

| Status | Meaning |
| --- | --- |
| `passed` | The check ran and succeeded. |
| `failed` | The check ran and did not succeed. |
| `blocked` | The check could not run: capability missing, path rejected, tool absent. |
| `not applicable` | The check has nothing to examine (no SVG embeds, no math). |
| `not requested` | The check is optional and was not asked for (e.g. a source-level audit). |

A checklist line MUST NOT be phrased so that it implies an operation happened.
Write "Reading-view render: blocked (no Obsidian CLI on PATH)", not "Rendered in
Obsidian ☑".

Frontmatter follows the same rule: `status: reconstructed` only after the
reconstruction is written and statically validated; `status: verified` only
after rendering and visual inspection actually passed. Otherwise use
`status: draft`.

## 6. Bounded fallback when rendering is unavailable

When no real Obsidian renderer can be controlled, do exactly this and stop:

1. Run the static validation layer and the append-integrity layer.
2. Report precisely which capabilities were unavailable and why.
3. List the exact note and diagram files that still need a one-time manual
   Reading-view check.
4. Do not state or imply that visual verification passed.

Do not search for workarounds, alternative renderers, or installation routes.
A generic Markdown preview is not a substitute: Obsidian, MathJax, Mermaid, the
active theme, and Excalidraw have to be exercised together, so a preview that
lacks them cannot support a rendering claim.

## 7. Completion report template

```markdown
**Mode:** reconstruct
**Target:** `AI/Theoretical AI/Attention.md` (appended)
**Agent block:** `20260805T141200Z-9f3ac1`
**Source pages:** `Attachments/attn-p1.jpg`, `Attachments/attn-p2.jpg` (user-attached, page order from visible numbering)
**Diagrams:** `Diagrams/Excalidraw/Attention/SVG/attention-qkv.svg` (new, source retained)

| Check | Status |
| --- | --- |
| Append integrity (prefix + boundaries) | passed |
| Static structural validation | passed |
| Transcription fidelity re-read | passed |
| Source-level technical audit | not requested |
| Obsidian Reading-view render | blocked — no `obsidian` on PATH |
| Screenshot visual inspection | blocked — no capture capability |

**Needs a one-time manual check:** `AI/Theoretical AI/Attention.md`,
`.../attention-qkv.svg`.

**Unresolved uncertainty:** page 2, third line — `[illegible: d_k / d_h]`;
transcribed with both readings shown.
```

Keep it to this shape. No retelling of the note's content.
